# 0002 宿主集成：薄适配层 + 原生核心

## 状态

已采纳。

## 背景

公式编辑能力必须出现在两个宿主里：Microsoft Word 与 WPS 文字。两者都支持在文档中插入可重新
编辑的对象，但扩展机制不同：Word 一侧的事实标准是加载项模板（`dotm`，配 Ribbon XML）或
COM 加载项；WPS 一侧官方提供的是 JS 加载项（`ribbon.xml` + `main.js` + `window.wps` JSAPI），
同时也能运行部分 Word 兼容的加载项与 VBA。

如果为每个宿主单独实现一遍公式编辑逻辑，编辑器行为、排版结果和格式转换会在三处（编辑器、
Word、WPS）逐渐漂移。反过来，如果试图把所有能力都塞进宿主进程内运行，就得把排版与渲染
搬进 COM/VBA 的世界，代价极高。

## 决策

1. **能力全部落在原生核心**：解析、排版、渲染、编辑模型都在 Rust crate 里；宿主只负责
   "取文档上下文、显示入口、把结果放回文档"。核心对外的两种接口是命令行
   （`--to/--from/--in/--out`，能被启动进程的宿主使用）与回环 HTTP（`--serve`，给以网页
   形式加载、无法启动进程的宿主使用），两者共用同一套转换实现。
2. **两个宿主各写一层薄适配**：
   - **主机制（两个宿主共用）：嵌入对象服务器。** 文档里的公式是我们注册的 OLE 嵌入对象；
     双击由宿主激活对象，服务器把公式交给编辑器进程（`--edit <file>` 交接），保存后写回
     对象存储并通知宿主落盘。Word 与 WPS 都走这一条，因此"双击编辑、保存回写"在两个宿主
     里行为一致。
   - Word：另有原生 COM Ribbon 加载项，提供插入/转换等命令。
   - WPS：另有 JS 加载项（`ribbon.xml` + `main.js`）作为便捷入口；它只是外壳，编辑能力
     来自嵌入对象服务器。注意 WPS 的 VBA/宏支持需要订阅或激活才能安装支持库，因此 WPS
     一侧**不依赖宏、不依赖 VBS/COM 自动化**。
3. **文档内承载格式分两层**：
   - 轻量互通：剪贴板写入 Office 原生公式（OMML）与 MathML/LaTeX 纯文本，让公式在不依赖
     我们的对象服务器时也能被 Word/WPS 原生识别与编辑。
   - 完整互通：自己的嵌入对象数据流，保存公式树与样式，支持重新打开后继续编辑。
4. **编号与交叉引用按字段实现**，即编号由域代码生成、引用指向该域，从而随章节变化自动更新。
5. **宿主与核心之间只有两种接口**：命令行（`--to/--from/--in/--out`，适合能启动进程的宿主与脚本）与回环 HTTP（`--serve`，适合以网页形式加载的宿主，如 WPS 的 JS 加载项，它们无法启动进程）。两种接口共用同一套转换实现，因此不会出现两个宿主行为不一致。HTTP 只绑定回环地址，随进程退出而结束。

## 备选方案

- **直接在 Word 的 COM 世界里实现编辑器**：宿主集成最"原生"，但编辑器与排版要重写成 COM
  组件，且无法复用于 WPS 与独立编辑器。
- **只做 Office.js/网页加载项**：跨平台，但插入可重新编辑的文档对象、批量处理现有公式、
  以及与旧版宿主兼容都受限，达不到目标功能面。
- **每个宿主各自实现一遍**：短期最快，长期必然分叉，且同一个公式在三处渲染出不同结果。

## 后果

- 原生库的 C ABI 成为稳定接口，需要版本化并保持向后兼容；宿主适配层的崩溃不能拖垮核心。
- WPS 与 Word 的命令面由同一份规格驱动，测试可以共享；差异只体现在适配层。
- 需要维护安装与注册脚本（两套），并把"加载项未启用"的排查路径写清楚。
