# 0001 公式模型与 crate 划分

## 状态

已采纳。

## 背景

需要一个能用 Rust 完整重建公式编辑能力的骨架：既要有所见即所得的编辑器，也要有面向
Word/WPS 的加载项和多种外部格式的互通。这些能力差异很大，如果都挤在一个 crate 里，
解析、排版、渲染与宿主集成的迭代节奏会互相牵制；如果拆得过细，又会把公式树这个唯一
真正共享的概念淹没在样板接口里。

## 决策

1. **以"公式树"为唯一共享契约。** `mt-core` 定义 `Math`、`Node`、`Path` 及全部模板，
   不依赖任何其它 crate，也不引入第三方依赖。
2. **统一的槽位模型。** 每个模板按视觉顺序暴露固定长度的槽位序列（`slot_count` /
   `slot` / `slot_mut`），编辑、排版、序列化都只走这个接口，不各自匹配节点类型。
   空行即空槽位，占位符由渲染层决定怎么画。
3. **按"数据流向"切 crate：** 输入输出格式各自成 crate（`mt-tex`、`mt-mathml`、
   `mt-omml`、`mt-mtef`），排版（`mt-layout`）与绘制（`mt-render`）分离，编辑模型
   （`mt-edit`）不依赖任何图形库，界面与加载项放在 `apps/`。
4. **转换器只依赖 `mt-core`；`mt-render` 依赖 `mt-layout`（消费其盒子树）。** 转换器不互相调用；需要组合时由上层（应用或加载项）
   串联，避免出现隐式的转换链。

## 备选方案

- **单 crate 起步，之后再拆。** 早期文件更少，但解析、排版、渲染与 COM/加载项依赖会很快
  在同一个依赖图里互相污染，且无法对"解析器不该依赖图形库"这类约束做机器校验。
- **用现成的表达式库作为内部表示。** 现成库多半以 TeX 或 MathML 为中心，而编辑器需要的是
  带槽位的模板树（"先插模板再填内容"的交互与二维光标导航都依赖它），转换层反而要来回搬运。
  故不使用，只在需要时作为对照。
- **把排版并入渲染。** 会让"同一棵公式树导出 SVG 与 PNG 结果一致"这类性质无法单独测试。

## 后果

- 新增能力通常意味着新增一个 crate，而不是往 `mt-core` 里加字段；`mt-core` 的变更需要
  同步全部下游。
- 排版与渲染分离，导出格式（PNG/SVG/EPS/WMF）可以逐个补，互不影响。
- 编辑模型不依赖图形库，因此光标与模板插入的行为可以用纯单元测试覆盖。

## 依赖

按 `CONTEXT.md` 的约定，新增第三方依赖在此说明理由。原则：标准库或自写小代码能解决的就不引；
引入的每一个都必须是「自己做要么更危险、要么明显更多代码」的那类。

| 依赖 | 用在哪 | 理由 |
| --- | --- | --- |
| `quick-xml` | `mt-mathml`、`mt-omml` | 解析**不可信** XML。手写解析要正确处理实体、属性引号、CDATA、编码与嵌套，正是容易出漏洞的地方；该 crate 的读取器直接在借用切片上工作，不需要中间缓冲。 |
| `cfb` | `mt-mtef` | 读写 OLE 复合文件容器（文档里的嵌入对象）。自实现复合文件的分段分配表与目录树属高风险低收益。 |
| `ttf-parser` | `mt-render`、`apps/*` | 从字体文件读字形轮廓与度量。排版与光栅化要的是字形数据而非文本整形，因此只要解析层，不引入整形栈。 |
| `png` | `mt-render` | 只做 PNG 编码；不引入完整图像处理栈。光栅化本身（轮廓填充、抗锯齿）是自写的。 |
| `eframe` + `egui` | `apps/mathtype` | 窗口与即时模式界面。自建平台层会让编辑器与核心的边界复杂化，而界面不是本项目的技术风险所在。 |
| `windows` / `windows-core` | `apps/ole-server`、`apps/word-addin` | COM/OLE 互操作（接口定义、注册、剪贴板、存储）。手写 vtable 与 GUID 不可维护。 |

字体资源：`crates/mt-render/assets/fonts/latinmodern-math.otf` 为 Latin Modern Math，采用 GUST Font License +
LPPL 1.3c 许可（`crates/mt-render/assets/fonts/LM-MATH-LICENSE.txt` 随字体一同入库），作为排版
与渲染的默认字形；其它字体一律运行时从本机读取，不入库。
